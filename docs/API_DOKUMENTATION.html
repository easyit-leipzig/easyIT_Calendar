Vollständige API-Dokumentation

Technische Referenz für die Kommunikation zwischen dem easyITCalendar-Frontend, nojquery.post.js, dem zentralen PHP-Handler und der MariaDB-Datenbank easyit_calendar.

JSON über POSTPHP 8.2+PDO / Prepared StatementsMariaDB 10.4CSRF-geschützt

1. Überblick

Die Kalender-API verwendet bewusst keinen klassischen REST-Endpunkt mit GET, PUT oder DELETE. Sämtliche Operationen laufen über einen zentralen PHP-Handler und werden durch das JSON-Feld action unterschieden.

Handler
api/calendar_handler.php
Transport
assets/js/nojquery.post.js
Datenbank
easyit_calendar
Frontend-Einstieg
index.php
Grundprinzip: Der Browser sendet JSON per POST. Der Handler validiert Sitzung, CSRF-Token und Nutzdaten, führt die Datenbankoperation aus und antwortet wiederum mit JSON.
ActionZweckErfolgsstatus
listTermine eines sichtbaren Zeitraums laden200
createTermin, Teilnehmer und Anlagen-Metadaten anlegen201
updateBestehenden Termin vollständig aktualisieren200
deleteTermin per Soft Delete deaktivieren200

3. Installation und Konfiguration

3.1 Voraussetzungen

  • Apache oder ein anderer PHP-fähiger Webserver
  • PHP 8.2 oder höher mit PDO-MySQL
  • MariaDB 10.4 oder kompatibel
  • Aktivierte PHP-Sessions

3.2 Datenbank importieren

sql/easyit_calendar_database.sql

Das Skript erzeugt die Datenbankstruktur, Rollen, Personen, Benutzer, Events, Teilnehmerzuordnungen, Anlagen und weitere Kalendertabellen.

3.3 API konfigurieren

<?php
return [
    'db' => [
        'host' => '127.0.0.1',
        'port' => 3306,
        'name' => 'easyit_calendar',
        'user' => 'root',
        'password' => '',
        'charset' => 'utf8mb4',
    ],
    'default_user_id' => 1,
    'attachments_path' => 'uploads/events',
];
Wichtig: default_user_id muss auf einen tatsächlich vorhandenen Datensatz in der Benutzertabelle zeigen. Der derzeitige Handler besitzt noch keine Benutzeranmeldung und verwendet deshalb diesen technischen Standardbenutzer.

3.4 Aufruf

http://localhost/easyIT_Calendar/index.php

Ein Aufruf über file:///... funktioniert nicht, weil PHP, Session und Datenbankzugriff einen Webserver benötigen.

4. nojquery POST-Transportschicht

4.1 Signatur

const result = await nj.post(url, data, options);
ParameterTypBeschreibung
urlStringZieladresse des PHP-Handlers.
dataObjektWird mit JSON.stringify() in den Request-Body geschrieben.
options.timeoutNumberZeitlimit in Millisekunden; Standard aus nj.config.ajaxTimeout oder 8000.
options.credentialsStringStandard same-origin; notwendig für die Session.
options.headersObjektZusätzliche Header, insbesondere X-CSRF-Token.
options.signalAbortSignalErmöglicht den externen Abbruch einer Anfrage.

4.2 Standardaufruf

const result = await nj.post(
  window.easyITCalendarHandler,
  {
    action: 'list',
    start: '2026-07-27',
    end: '2026-08-03'
  },
  {
    headers: {
      'X-CSRF-Token': window.easyITCalendarCsrf
    }
  }
);

4.3 Transportverhalten

  • HTTP-Methode: POST
  • Accept: application/json
  • Content-Type: application/json; charset=UTF-8
  • cache: no-store
  • credentials: same-origin

Bei ungültigem JSON, HTTP-Fehlern oder {"ok":false} wirft nj.post() ein JavaScript-Error-Objekt. Der HTTP-Status steht zusätzlich in error.status, die Serverantwort in error.response.

5. Allgemeines Request-/Response-Protokoll

5.1 Endpunkt

POST api/calendar_handler.php

5.2 Erforderliche Header

Content-Type: application/json; charset=UTF-8
Accept: application/json
X-CSRF-Token: <Token aus index.php>

5.3 Minimaler Request

{
  "action": "list",
  "start": "2026-07-27",
  "end": "2026-08-03"
}

5.4 Erfolgsantwort

{
  "ok": true,
  "action": "list",
  "events": []
}

5.5 Fehlerantwort

{
  "ok": false,
  "error": "Beschreibung des Fehlers"
}
Datumslogik: Beim Laden ist end exklusiv. Der Bereich 2026-07-27 bis 2026-08-03 umfasst damit den 27. Juli 00:00 Uhr bis unmittelbar vor den 3. August 00:00 Uhr.

6. Aktion list

Lädt alle aktiven Termine, die den angeforderten Zeitraum schneiden.

6.1 Request

{
  "action": "list",
  "start": "2026-07-27",
  "end": "2026-08-03"
}
FeldPflichtFormatBedeutung
actionjalistWählt die Ladefunktion.
startjaYYYY-MM-DDInklusive Untergrenze.
endjaYYYY-MM-DDExklusive Obergrenze; muss nach start liegen.

6.2 Auswahlbedingung

e.activ = 1
AND e.start < range_end
AND e.end >= range_start

Dadurch werden auch Termine geliefert, die vor dem sichtbaren Zeitraum beginnen oder nach ihm enden, ihn aber überlappen.

6.3 Response

{
  "ok": true,
  "action": "list",
  "events": [
    {
      "id": 15,
      "to_role": 3,
      "to_tutor": 1,
      "to_student": 2,
      "start": "2026-07-27T09:00:00",
      "end": "2026-07-27T10:30:00",
      "activ": true,
      "thema": "Mathematik",
      "description": "Lineare Gleichungen",
      "appendizies": ["arbeitsblatt.pdf"],
      "version_no": 2
    }
  ]
}
Kompatibilitätsfelder: to_tutor, to_student und to_role werden aus der normalisierten Tabelle event_participants abgeleitet. Bei mehreren Personen liefert diese API-Version jeweils nur die primär markierte Person.

7. Aktion create

Legt einen neuen Eventdatensatz an und speichert anschließend Teilnehmerzuordnungen und Anlagen-Metadaten in derselben Transaktion.

7.1 Request

{
  "action": "create",
  "to_role": 3,
  "to_tutor": 1,
  "to_student": 2,
  "start": "2026-07-27T09:00:00",
  "end": "2026-07-27T10:30:00",
  "activ": true,
  "thema": "Mathematik",
  "description": "Lineare Gleichungen",
  "appendizies": ["arbeitsblatt.pdf", "notizen.docx"]
}

7.2 Validierung

  • start und end müssen exakt YYYY-MM-DDTHH:MM:SS entsprechen.
  • end muss nach start liegen.
  • thema wird auf 255 Zeichen gekürzt.
  • IDs kleiner als 0 werden auf 0 begrenzt; to_role mindestens auf 1.
  • Anlagennamen werden getrimmt, leere Werte entfernt und Duplikate beseitigt.

7.3 Response

HTTP 201
{
  "ok": true,
  "action": "create",
  "id": 42
}

7.4 Speicherung

  • events: Kerndaten des Termins
  • event_participants: primärer Tutor und primärer Student
  • event_attachments: Dateinamen und berechnete Speicherpfade

8. Aktion update

Aktualisiert einen vorhandenen Termin vollständig. Die Aktion wird sowohl vom Bearbeitungsdialog als auch beim Drag-and-drop verwendet.

8.1 Request

{
  "action": "update",
  "id": 42,
  "to_role": 3,
  "to_tutor": 1,
  "to_student": 2,
  "start": "2026-07-27T10:00:00",
  "end": "2026-07-27T11:30:00",
  "activ": true,
  "thema": "Mathematik",
  "description": "Verschobener Termin",
  "appendizies": ["arbeitsblatt.pdf"]
}

8.2 Verhalten

  1. Eventfelder werden aktualisiert.
  2. version_no wird um 1 erhöht.
  3. Vorhandene Teilnehmerzuordnungen werden gelöscht und neu angelegt.
  4. Vorhandene Anlagen-Metadaten werden gelöscht und neu angelegt.
  5. Alle Schritte laufen in einer Datenbanktransaktion.

8.3 Response

HTTP 200
{
  "ok": true,
  "action": "update",
  "id": 42
}
Aktueller Stand: Die API liefert version_no beim Laden und erhöht es beim Update, prüft jedoch noch keine vom Client mitgesendete Versionsnummer. Ein vollständiger Schutz vor parallelem Überschreiben ist deshalb vorbereitet, aber noch nicht aktiv.

9. Aktion delete

Deaktiviert einen Termin. Der Datensatz wird nicht physisch aus der Datenbank entfernt.

9.1 Request

{
  "action": "delete",
  "id": 42
}

9.2 Datenbankwirkung

UPDATE events
SET activ = 0,
    version_no = version_no + 1,
    updated_by = :user
WHERE id = :id AND activ = 1

9.3 Response

{
  "ok": true,
  "action": "delete",
  "id": 42
}
Vorteil des Soft Delete: Historische Zuordnungen bleiben erhalten. Eine spätere Wiederherstellungs- oder Archivfunktion kann darauf aufbauen.

Das API-Format bleibt aus Kompatibilitätsgründen flach, während die Datenbank mehrere Personen und Rollen pro Termin unterstützen kann.

12. Sicherheit

12.1 Bereits umgesetzt

  • CSRF-Schutz mit zufälligem Session-Token und hash_equals()
  • Ausschließlich POST am zentralen Handler
  • JSON-Body statt gemischter Formulardaten
  • PDO Prepared Statements
  • Deaktivierte emulierte Prepared Statements
  • Transaktionen bei create und update
  • Serverseitige Datums- und ID-Validierung
  • Keine Ausgabe interner Exception-Details an den Client
  • Cache-Control: no-store

12.2 Noch zu ergänzen

  • Login- und Rollenprüfung je Action
  • Ersetzung von default_user_id durch die angemeldete Benutzer-ID
  • Prüfung, ob Tutor, Student und Rolle tatsächlich existieren und aktiv sind
  • Aktive optimistische Sperre über version_no
  • Rate Limiting beziehungsweise Missbrauchsschutz
  • Strenge Upload-Prüfung für zukünftige echte Dateiuploads
  • Audit-Log-Einträge für create, update und delete

13. Frontend-Integration

13.1 Globale Konfiguration aus index.php

window.easyITCalendarHandler = "api/calendar_handler.php";
window.easyITCalendarCsrf = "...";

13.2 Termine laden

async function loadEvents(start, end) {
  const result = await nj.post(
    window.easyITCalendarHandler,
    { action: 'list', start, end },
    { headers: { 'X-CSRF-Token': window.easyITCalendarCsrf } }
  );
  return result.events;
}

13.3 Termin speichern

async function saveEvent(event) {
  const action = event.id ? 'update' : 'create';
  return nj.post(
    window.easyITCalendarHandler,
    Object.assign({ action }, event),
    { headers: { 'X-CSRF-Token': window.easyITCalendarCsrf } }
  );
}

13.4 Termin löschen

async function removeEvent(id) {
  return nj.post(
    window.easyITCalendarHandler,
    { action: 'delete', id },
    { headers: { 'X-CSRF-Token': window.easyITCalendarCsrf } }
  );
}

13.5 Blättern

Bei jedem Wechsel von Tag, Woche oder Monat berechnet das Frontend den sichtbaren Zeitraum und ruft anschließend list neu auf. Die API überträgt dadurch nur die erforderlichen Termine.

14. Erweiterung des zentralen Handlers

Neue Funktionen werden durch zusätzliche Action-Werte ergänzt. Empfohlen ist eine fachliche Namensstruktur, beispielsweise:

persons.list
roles.list
contacts.list
blocks.list
blocks.create
blocks.delete
attachments.upload
settings.load
settings.save

14.1 Beispiel: neue Action registrieren

switch ($action) {
    case 'list':
        list_events($pdo, $input);
        break;
    case 'persons.list':
        list_persons($pdo, $input);
        break;
    default:
        throw new InvalidArgumentException('Unbekannte Aktion.');
}

14.2 Beispiel: Antwortfunktion

function list_persons(PDO $pdo, array $input): never
{
    $stmt = $pdo->query(
        'SELECT id, firstname, lastname FROM persons WHERE activ = 1 ORDER BY lastname, firstname'
    );
    json_response([
        'ok' => true,
        'action' => 'persons.list',
        'persons' => $stmt->fetchAll()
    ]);
}
Empfehlung: Wenn der Handler weiter wächst, sollte jede Fachdomäne in eine eigene Handlerklasse oder Service-Datei ausgelagert werden, während calendar_handler.php nur Routing, Authentifizierung und Antwortformat übernimmt.

16. Aktuelle Grenzen und empfohlene nächste Schritte

  1. Echte Mehrfachteilnehmer: Die Datenbank kann mehrere Teilnehmer, das aktuelle Frontend-/API-Kompatibilitätsformat zeigt jedoch nur primäre Tutor- und Student-IDs.
  2. Anlagen: Der Handler speichert derzeit nur Dateinamen und berechnete Pfade. Binärdateien werden noch nicht hochgeladen.
  3. Optimistische Sperre: version_no wird erhöht, aber noch nicht als Update-Bedingung geprüft.
  4. Benutzer und Rechte: CRUD-Aktionen sind CSRF-geschützt, aber noch nicht rollenbasiert autorisiert.
  5. Referenzprüfung: Personen- und Rollen-IDs sollten vor dem Speichern gegen aktive Datensätze geprüft werden.
  6. Blockierte Bereiche: Die Frontendfunktion sollte als eigene API-Domäne blocks.* mit DB-Persistenz ergänzt werden.
  7. Auswahllisten: Numerische Eingabefelder sollten durch datenbankgestützte Rollen-, Tutor- und Teilnehmer-Selects ersetzt werden.
Empfohlene Ausbaureihenfolge: zuerst Rollen/Personen-API und Selectfelder, danach Blockierungen, anschließend echter Datei-Upload, Authentifizierung/Rechte und zuletzt Audit-Log sowie optimistische Sperre.
